## Goal

A customer can place a Takeaway or Delivery order, or book a table with an optional pre-order, on one slot engine. Payment is on site or by bank transfer (Phase 1). Stock moves in the same transaction as the confirmation and comes back on cancellation. Staff manage orders and reservations from the admin. Event seats are booked without overbooking. Every step sends an e-mail in the customer's language. Reloading or retrying never duplicates anything.

## In scope / out of scope

- **In:** the tasks below.
- **Out:** wallee (M4.1; the `PaymentProvider` interface is built so wallee plugs in later), mobile staff screens (M3.1; staff use the admin for now), invoices (M3.2).

## Tasks

### T1 · Slot engine (pure)
Files: `modules/sales/slots.ts` (+ test).

- `generateSlots({ date, rule, hours, closedDates, now, taken })` → `{ from, to, available }[]`. Slots fall inside the opening hours, at `intervalMin` steps, start no earlier than `now + leadTimeMin`, fall within `maxDaysAhead`, return nothing on closed dates, and `available = capacity − taken[from]` (orders, or guests for `table`).
- All times use the Europe/Luxembourg timezone via `lib/time.ts`, including the DST change days.
- Vectors (≥ 8): normal day; lead time cuts the first slots; closed date → []; a slot at capacity → `available 0`; table capacity counts guests; the last slot ends at closing time; the DST spring-forward day (29 Mar 2026 pattern, using the next occurrence) produces no non-existent local times; `maxDaysAhead + 1` → [].

### T2 · Delivery zones (pure)
Files: `modules/sales/zones.ts` (+ test).

- `resolveZone(postalCode, zones)` → zone or `null`. Normalize "L-1234", "l 1234" and "1234" to `1234`.
- `deliveryFee(zone, subtotalCents)` → `{ feeCents, belowMinimum }`.
- Vectors: inside, outside → null (the UI suggests takeaway), below minimum, at or above the free threshold → 0, inactive zone ignored.

### T3 · Order state machine (pure)
Files: `modules/sales/order-states.ts` (+ test).

- `ORDER_FLOW` (`03-CODING-LAWS.md` §4.6) and `RESERVATION_FLOW` (`pending → accepted | rejected | cancelled`, `accepted → completed | cancelled`).
- `canTransition(from, to)` and `effects(from, to)` → a list of `'postSale' | 'returnStock' | 'mailCustomer' | 'mailStaff' | 'outbox'`. The effects are data, so they can be tested without I/O.
- Vectors: every allowed move and a sample of forbidden ones; `confirmed → cancelled` includes `returnStock`; `pending → cancelled` does not (stock was never posted).

### T4 · Orders, payments interface, `placeOrder`
Files: `modules/sales/{collections,service,actions}.ts`, `modules/payments/{collections,service,provider}.ts`, `modules/payments/providers/manual.ts`.

- `PaymentProvider` interface: `start(order) → { status: 'confirmed' | 'awaiting_payment', redirectUrl? }`, `capture(order)`, `void(order)`, `refund(order, amountCents)`. The `manual` provider: `onsite` and `invoice` → `confirmed` (to be paid at pickup or later); `transfer` → `awaiting_payment` (staff mark it paid). Capture, void and refund on `manual` record a `payments` row and return.
- `placeOrder` (`publicAction`) implements `02-ARCHITECTURE.md` §6 exactly:
  - The input carries the client-generated `idempotencyKey` (`crypto.randomUUID()` created when checkout opens and kept in sessionStorage, so a reload reuses it).
  - Every check runs inside the transaction: zone and minimum for delivery, slot availability recounted in the transaction, and stock via `postMovements` when confirming.
  - A duplicate key → return the existing order (no error, no second e-mail).
  - On commit, `after()` sends the e-mails.
- `transition(orderId, to, { user, reason? })` (staff action): checks `canTransition`, runs `effects` in one transaction, and sets `stockPosted`. `returnStock` posts `cancel` movements equal to the original sale movements with the opposite sign, found by `ref`, so the return is always exact and never posted twice.
- Admin: order status is read-only, and the edit view shows custom buttons for the allowed transitions only. List columns: number, channel, mode, slot, customer, total, status. Default filter: today and upcoming.

### T5 · Checkout UI
Files: `app/(site)/[locale]/checkout/page.tsx`, `order/[id]/page.tsx`, `modules/webshop/components/{checkout-form,slot-picker}.tsx`.

- One page with three mode tabs (the prototype's pickup, delivery and table switch) and the prototype's field sets per mode. A logged-in customer's contact and default address are pre-filled.
- `SlotPicker`: a date with `calendar` + `popover`, then time chips (`Button variant="chip"`) from a `slotsFor(mode, date)` action. Full slots are disabled.
- Delivery: entering the postal code shows the fee, minimum and free threshold live, or "outside zone → choose takeaway".
- Table: guests stepper, an optional "pre-order" toggle that shows the cart lines, and the reservation is created as `pending` (with its pre-order order also `pending`).
- Payment choice (Phase 1): "Pay on site" (pickup, table) and "Bank transfer" (delivery, and pickup as an option). The labels come from the dictionaries.
- The order confirmation page `/order/[id]` is accessible to the owner or via a signed token in the URL for guests (an HMAC of the id with `PAYLOAD_SECRET`). It shows the status, slot, lines, totals and transfer details (IBAN from private settings) when relevant.
- The cart's "Checkout" button is now shown (M2.2 T3).

### T6 · Reservations and event bookings
Files: `modules/sales/reservations.ts`, `modules/events/{service,actions}.ts`, admin buttons.

- Reservation actions for staff: `accept` (the pre-order becomes `confirmed` → stock posted), `reject` and `cancel` (no stock), `complete`. Each sends the e-mail in the customer's language.
- Event booking: `bookEvent` (`publicAction`, idempotent) with a conditional `$inc` on `events.booked` (`04-DATA-MODEL.md` §4). Free events → `confirmed`; paid events → `pending` with "pay on site" in Phase 1. Port `ReserveDialog` with `Field`, `QtyStepper` and `ActionForm`, and show the Reserve button (hidden since M1.3). Seats left are shown when ≤ 10.

### T7 · E-mails
Files: `modules/notifications/templates/{order-received,order-status,reservation,event-booking}.tsx`.

- Customer: order received (with transfer details if relevant), status changed (confirmed, ready, out for delivery, cancelled), reservation pending, accepted or rejected, event booking. Staff: new order, reservation or booking, sent to `MAIL_STAFF_TO`.
- All templates use the shared layout, the order's `locale`, and `formatMoney`. Each one is sent once per transition, and the idempotency is guaranteed because the send runs in `after()` only when the transaction actually changed state.

### T8 · Tests
- Unit: slots, zones, order-states (T1–T3).
- Integration (`modules/sales/orders.int.test.ts`):
  - Same `idempotencyKey` twice (sequential and parallel) → 1 order, 1 movement set, the second call returns the same id.
  - Confirm then cancel → stock back to the start; cancel again → rejected by the state machine, stock unchanged.
  - The last slot taken by 2 parallel orders → one succeeds, one gets `CONFLICT`.
  - Reservation reject → no movements; accept → movements equal the pre-order lines.
  - The last event seat booked in parallel → one success.
  - A guest order page token for order X does not open order Y.
- E2E: `tests/e2e/checkout.spec.ts` (`06-TESTING.md` §3.3 #2), reading the e-mail from Mailpit's API.

## Acceptance criteria

- **AC-M2.3-01 [V-CART]** Given each mode (pickup, delivery, table + pre-order), when a test order is placed, then it appears in the admin with the correct mode, slot, totals and status, and the customer receives the e-mail in their language.
- **AC-M2.3-02 [R2] [V-CART]** Given a confirmed webshop order, then its stock movements exist with `channel: webshop` and `ref` = the order. Given it is cancelled, then equal and opposite `cancel` movements exist.
- **AC-M2.3-03 [R2]** Given a reload or double submit of checkout, then there is still exactly one order, one set of movements and one e-mail.
- **AC-M2.3-04 [V-CART]** Given a postal code outside every zone, then delivery is refused with an invitation to choose takeaway. Given a subtotal below the zone minimum, then checkout is blocked with the minimum shown.
- **AC-M2.3-05 [V-CART]** Given a slot at capacity, then it is shown disabled and a forged request for it fails.
- **AC-M2.3-06 [V-PAY]** Given a rejected reservation with a pre-order, then no payment is recorded and no stock moves.
- **AC-M2.3-07 [V-CONT]** Given an event with 1 seat left and two simultaneous bookings, then one succeeds and the other sees "sold out".
- **AC-M2.3-08 [V-PAY]** Given a bank-transfer order, then it is `awaiting_payment`, the e-mail and confirmation page show the IBAN and reference, and staff can mark it paid → `confirmed` → stock posted.
