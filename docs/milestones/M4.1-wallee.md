## Goal

Add card payment as a **second adapter** behind the `PaymentProvider` interface from M2.3, with no change to `placeOrder`, `transition` or the checkout UI apart from a new payment choice. An order is marked paid **only** when wallee confirms it, verified on the server. Pre-orders are authorised and then captured on Accept or voided on Reject. Staff can send a payment link or show a QR code for mobile sales, quotations and invoices. No card data ever touches the application.

## In scope / out of scope

- **In:** the tasks below.
- **Out:** the live space and activation (APPLUX, Q§08), transaction fees, Twint and other methods beyond what the wallee Payment Page offers by configuration.

## Tasks

### T1 · Client and configuration
Files: `modules/payments/providers/wallee/client.ts`, `lib/env.ts`.

- A small client with the operations used: `createTransaction`, `paymentPageUrl`, `read`, `complete`, `void`, `refund`, `createPaymentLink`. Each logs to `integrationLogs` (request summary without secrets, status, duration).
- Test-space credentials only. The adapter is enabled when the env vars are present **and** `BusinessSettings` enables card payment. Otherwise the checkout never offers it.

### T2 · Checkout payment (webshop)
Files: `modules/payments/providers/wallee/index.ts`, checkout payment choice.

- `start(order)`: create the transaction server-side (line items, amounts in cents and EUR from the order snapshot, the order's locale as language, success and failure URLs to `/[locale]/order/[id]?t=…`, `merchantReference` = order number). Store the wallee transaction id in a `payments` row (`authorization` or `charge`) and return `{ status: 'awaiting_payment', redirectUrl }`. The order waits in `awaiting_payment`, and **stock is not posted yet**.
- Return pages are informational only. They show "processing" until the webhook has confirmed. They never mark anything paid.
- Stock reservation choice: stock is posted when the payment is confirmed. To avoid paying for an item that has just sold out, `start` re-checks availability, and confirmation runs `postMovements` with the normal guard. If the guard fails after payment (an extremely rare race), the order goes to `confirmed` with an `OUT_OF_STOCK` staff alert e-mail instead of failing: the customer has paid, and staff decide on a refund. Record this as decision D-07.
- Abandoned `awaiting_payment` orders older than the transaction expiry are cancelled by a cron job `payments-expire`, with no stock to return.

### T3 · Webhook (single source of truth for "paid")
Files: `app/api/webhooks/[provider]/route.ts`, `modules/payments/providers/wallee/webhook.ts` (+ test).

1. Verify the signature exactly as documented. If it is invalid → 401 and logged.
2. Use the entity id from the body to **re-read the transaction from the API**. Never trust the body's state.
3. Map the state to our `payments` rows and the order transition **in one transaction**. It is idempotent: a `payments` row with the same `providerRef` and kind already processed → no-op, 200.
4. The response is 200 for anything processed or already processed, so wallee stops retrying, and 5xx only when our DB is unavailable.

State mapping (to be confirmed against the docs in T1): authorised → `payment.status: authorized` (pre-orders stay `pending` until Accept); fulfilled or completed → `paid` + transition `awaiting_payment → confirmed`; failed or declined → the order stays `awaiting_payment` and the customer can retry from the order page with a new transaction; voided → `voided`.

### T4 · Pre-orders: deferred capture
Files: `modules/sales/reservations.ts` (effects), `modules/payments/providers/wallee/index.ts`.

- Checkout for a table + pre-order offers "Pay at the restaurant" (`manual`) or "Online authorisation" (wallee, transaction created **without completion**).
- `accept` → `capture(order)` (complete) **before** confirming. If the capture fails, the reservation stays `pending` and staff see the error.
- `reject` and `cancel` → `void(order)`. The authorisation-window limitation (Q§08, Rev 1.1) is shown to staff: a reservation pending longer than the window displays a warning, and acceptance then asks the customer to pay on site.

### T5 · Refunds
- The `refunded` transition with a wallee payment → `refund(order, amount)` → a `payments` row of kind `refund`. The order becomes `refunded` when wallee confirms it (webhook or synchronous response, as documented). The stock return and the credit note (M3.2) run as before.

### T6 · Payment links and QR (mobile sale, quotation, invoice)
Files: `modules/payments/actions.ts` (`createPaymentLink`), staff sale screen, quotation and invoice admin buttons.

- `createPaymentLink(target)` for an order (mobile sale), a sent quotation or an unpaid invoice: an amount equal to the amount due, the reference, single use. Returns the URL. Staff can **e-mail** it (template in the customer's locale) or **show a QR code** (`qrcode`) full-screen on the staff phone so the customer can pay on the spot.
- The webhook marks the order or invoice paid (`markInvoicePaid` is called by the webhook path, the same function staff use for bank transfers).

### T7 · Tests
- Unit: `webhook.test.ts`: valid signature, tampered body, wrong key, missing header.
- Integration (the wallee client mocked at the module boundary; the webhook route is called as a function): a replayed "fulfilled" webhook → one `payments` row, one confirmation, one movement set, one e-mail; a body claiming "fulfilled" when the API read says "failed" → nothing paid; reject a pre-order → `void` called, no movements, no capture; a refund → credit note + stock returned once.
- Manual against the wallee **test space** (T8 checklist), because the e2e suite does not drive the external Payment Page.

## Acceptance criteria

- **AC-M4.1-01 [V-PAY]** Given test orders in the wallee test space for pickup, delivery and table + pre-order, including a declined card and a cancelled payment, then each order ends in the correct state and only fulfilled payments are marked paid.
- **AC-M4.1-02 [V-PAY]** Given a webhook delivered twice, or a reload of the return page, then there is exactly one payment row, one confirmation e-mail and one set of stock movements.
- **AC-M4.1-03 [V-PAY]** Given a rejected reservation with an online authorisation, then the authorisation is voided and the customer is never charged.
- **AC-M4.1-04 [V-PAY]** Given a refund in the admin, then wallee shows the refund, a credit note is issued, and stock is returned once.
- **AC-M4.1-05 [V-PAY] [R5]** Given a mobile sale, a quotation or an invoice, when staff show the payment QR and the customer pays, then the order or invoice becomes paid with no staff action.
- **AC-M4.1-06 [V-PAY]** With wallee env vars removed, the site works exactly as in Phase 1 (`manual` only), with no error.
