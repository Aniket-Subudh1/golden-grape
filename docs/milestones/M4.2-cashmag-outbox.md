## Goal

Connect CashMag through the `PosConnector` interface from M3.3, **if** an API is documented and accessible. Web orders are pushed one way to CashMag, and in-store sales are read back automatically if the API exposes them. Selling never waits for the POS. When CashMag is down or absent, every channel keeps working and the outbox catches up.

## Tasks

### T1 · Adapter
Files: `modules/pos/adapters/cashmag.ts`.

- Implements `PosConnector`:
  - `pushOrder(order)` maps the order through the documented product, VAT and status mapping. Products are matched by barcode or SKU, because the platform is the product master (Q§07). It is idempotent on the CashMag side, using the order number as the external reference if the API supports one. Otherwise our `integrationLogs` success record prevents a second push.
  - `pullSales(since)` runs only if the API exposes sales.
  - `health()` is a cheap authenticated call.
- Unmapped products → the push fails with a clear error naming the SKU, the row goes `failed`, and staff fix the mapping and press Retry.
- Settings: `pos.adapter` (`none`, `csv`, `cashmag`), and the mapping table (VAT key → CashMag VAT code, order mode → CashMag order type).

### T2 · Automatic sales read (if available)
Files: `modules/pos/jobs.ts` (`pos-pull`).

- A cron job every 15 min (or as rate limits allow): `pullSales(lastCursor)` → the same import path as the CSV (M3.3 T5: one `pos` order per receipt + `pos_import` movements) → store the cursor in `posImports` as a synthetic import keyed by `cashmag:<receiptId>`, so a receipt is never imported twice, whether it came by API or by CSV.
- If the API has no sales read, the daily CSV import remains the process, and the user guide (M4.3) says so.

### T3 · Outbox hardening
- Confirm the M3.3 processor with the real adapter: the claim is atomic, a crash mid-send is safe (rows stuck in `sending` for more than 10 min return to `pending`), the backoff schedule follows `02-ARCHITECTURE.md` §6, the dead-letter alert e-mail is sent, and Retry works.
- Admin integration log: filter by target, ok or failed, and date; payloads are viewable for debugging, with secrets never logged.
- Error alerts: the first failure of a row is logged only; `dead` sends an e-mail; `health()` failing for more than 30 min sends one e-mail (throttled to 1 per 6 h).

### T4 · Tests
- Unit: the order → CashMag payload mapping (VAT codes, packaging lines expanded or sent as the configured unit, totals equal to the order).
- Integration (adapter HTTP mocked at `fetch`): a successful push → the row `sent` and a log entry; a 500 response → backoff; 5 failures → `dead` + e-mail; a stale `sending` row is recovered; a pulled receipt imported twice → one order.
- Manual against the CashMag test environment (checklist).

## Acceptance criteria

- **AC-M4.2-01 [R3]** Given CashMag test credentials, when a web order is confirmed, then it appears in CashMag with matching lines and totals, and the integration log shows the request.
- **AC-M4.2-02 [R3]** Given CashMag unreachable, when orders are placed, then they succeed immediately. The outbox retries with backoff, and Retry sends them once CashMag is back.
- **AC-M4.2-03 [R3]** Given the API exposes sales, then in-store sales appear in the platform within the polling interval with channel `pos` and reduce stock once.
- **AC-M4.2-04 [R3]** Given CashMag disconnected (`pos.adapter: none` or `csv`), then every channel keeps selling and `rebuild-stock --check` reports no difference.
- **AC-M4.2-05 [R3]** The module overview (M4.3) explains how to add another POS adapter by implementing `PosConnector` alone, without touching the shop.
