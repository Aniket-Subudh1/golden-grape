## Goal

Complete Phase 1. Customers can leave a Google review from a QR code, and the site shows the rating and recent reviews. Employees check in and out with a daily QR code, and managers get the monthly hours. Owners see sales by any dimension and export CSV. In-store CashMag sales enter the stock ledger by daily CSV, with no API. Domain events queue in an outbox, ready for the M4.2 connector.

## Tasks

### T1 · Google Reviews
Files: `modules/reviews/{globals,service,jobs}.ts`, `app/(site)/[locale]/r/route.ts` (short-link redirect), `components/site/home/social-proof.tsx` (data swap), an admin view.

- Settings: `reviews.placeId` and `reviewUrl` (default `https://search.google.com/local/writereview?placeid=<placeId>`).
- Short link `/r` → 302 to `reviewUrl`. A printable QR (PNG and SVG download, an admin button) encodes `APP_URL/r`, for table cards, receipts and packaging.
- `refreshReviews()` (cron job `reviews-refresh`, daily) calls the Places API (New) Place Details with the field mask `rating,userRatingCount,reviews`. Check the current endpoint and field names against Google's docs at implementation time. It stores the result in `ReviewsCache` with the attribution. On error it keeps the previous cache and logs to `integrationLogs`.
- Website: the prototype's `SocialProof` section shows the rating, count and up to 5 reviews from the cache with Google attribution and a "Leave a review" button (`/r`). The section is hidden when the cache is empty.
- Admin overview: rating, count, the cached reviews, the last refresh, and a "Refresh now" button. **Reading all reviews and replying** via the GBP API is built only if DEP-09 gives API access. Otherwise the admin shows a direct link to the Google Business Profile (Q§09). Record which case applies in PROGRESS.

### T2 · Attendance QR token (pure)
Files: `modules/attendance/qr-token.ts` (+ test).

- `dailyToken(day, secret)` = base64url HMAC-SHA256 of `attendance:<YYYY-MM-DD Luxembourg>`, truncated to 16 bytes. `verify(token, now, secret)` accepts today's token, plus yesterday's until 03:00 to cover night shifts closing after midnight. Comparison is constant-time.
- Vectors: today valid; yesterday valid at 02:59 and invalid at 03:01; tomorrow invalid; tampered invalid; DST day correct.

### T3 · Attendance
Files: `modules/attendance/{collections,service,actions}.ts`, `app/(staff)/staff/attendance/page.tsx`, `app/(staff)/staff/attendance/qr/page.tsx` (venue display).

- Venue display (`/staff/attendance/qr`, manager login, kept open on a tablet): a full-screen QR of `APP_URL/staff/attendance?t=<dailyToken>`, refreshed automatically after midnight.
- The employee scans it with their own phone camera → staff login if needed (any user with the `attendance` role) → one big button: "Check in" or "Check out", depending on the open record. `checkInOut(user, token)` verifies the token, then in one transaction closes the open record or creates one. The partial unique index guarantees one open record. Rate limit: 1 per 30 s per user. **No geolocation is recorded** (Q§09).
- Manager (`/staff/attendance` manager tab + admin): who is checked in now, history per employee, and corrections (set a missing check-out or fix a time) with a required reason → `attendanceCorrections` + `audit`.
- Monthly report: hours per employee per day and total (an open record counts 0 until corrected and is flagged), plus a CSV export. It is a Payload custom admin view and a staff screen for managers, and both call the same `monthlyReport(month)`.

### T4 · Sales dashboard
Files: `modules/reporting/{service,summary}.ts` (+ test), `app/(payload)/admin/...` custom view `Dashboard` (Payload `admin.components.views` or `afterDashboard`; use whichever the installed version supports).

- `salesSummary({ from, to, groupBy: 'day'|'product'|'brand'|'category'|'customer'|'channel', channel? })`: a Mongo aggregation over `orders` with status in (`confirmed`, `ready`, `out_for_delivery`, `completed`), minus refunded credit amounts. It returns revenue (gross), net, VAT, order count and average basket per group, plus the totals row. Range boundaries are Luxembourg-local days (`lib/time.ts`).
- The pure `summary.ts` folds the aggregation rows into totals and averages and is unit-tested. The Mongo aggregation itself is covered by one integration test against known orders.
- UI: the date range (today, 7 days, month, custom), group-by tabs, a total cards row, a simple bar list (CSS widths, no chart library), a table, and "Export CSV". Visible to admin and manager only.
- The P3 acceptance "dashboard totals reconcile with the order list for any date range" is a test (T6).
- **Built early (9 Nov):** `modules/reporting/{summary,service}.ts` with the totals (`salesSummary({ from, to })`, `salesOverview`), `summary.test.ts` and the reconciliation test `service.int.test.ts`; a sale counts on its `slot.date`. The admin home shows them as key figures. Still to build here: `groupBy` (only the `$group` `_id` changes; `totals()` already folds group rows), the channel filter, and the dashboard page with range, tabs, bars, table and CSV.

### T5 · POS connector interface, CSV import, outbox
Files: `modules/pos/{collections,connector,service,actions,jobs}.ts`, `modules/pos/adapters/csv.ts`, `modules/pos/csv.ts` (+ test).

- `PosConnector` interface: `pushOrder(order)`, `pullSales(since)`, `health()`. Adapters live in `modules/pos/adapters/`. `connector()` returns the configured adapter, or a `none` adapter whose `pushOrder` is a no-op that marks the row `sent` with note `no-pos`, so the outbox never piles up when no POS is connected.
- Outbox: `pos.enqueue(tx, topic, payload)` is called by `placeOrder` and `transition` (confirmed, cancelled, refunded) **inside their transactions**, only when `isModuleOn('pos')`. The processor (`outbox-process` cron, every minute) claims due rows atomically (`findOneAndUpdate` status `pending` → `sending`), calls the adapter, and on failure sets backoff and `attempts + 1`. After 5 attempts it marks the row `dead` and e-mails `alerts.outboxAlertEmail`. The admin outbox list has a "Retry" button on `failed` and `dead` rows. Built here and exercised with the `none` adapter; M4.2 adds CashMag.
- CSV import: the admin upload (or `/staff` for managers) runs `parseSalesCsv(text, mapping)` (pure: delimiter detection `,`/`;`, decimal comma, configurable column mapping stored in settings `pos.csvMapping`) → rows `{ receipt, date, barcode|ref, qty, unitPriceCents }` → matched to a variant or unit by barcode, then SKU → preview (matched, unmatched, totals). Confirm runs in one transaction: the file hash must be unique, one `orders` doc per receipt (`channel: 'pos'`, `mode: 'instore'`, status `completed`, `payment.status: paid`, `slot.date`/`slotAt` = the receipt's day and time, the sale day for T4), and `postMovements` with type `pos_import` (it never blocks on negative stock; a negative result is flagged per `02-ARCHITECTURE.md` §5.1). Unmatched rows are listed and can be fixed (assign a variant) and re-confirmed in the same import.

### T6 · Tests
- Unit: `qr-token.test.ts` (T2), `csv.test.ts` (semicolon + decimal comma; BOM; quoted fields; an unknown barcode → unmatched; a packaging barcode → factor applied), `summary.test.ts` (totals, average basket with 0 orders = 0).
- Integration:
  - The same CSV file twice → the second import is rejected (hash); a matched row posts a `pos_import` movement and a `pos` order.
  - Two parallel check-ins → one open record.
  - `salesSummary` total for a range = the sum of the order totals listed by the admin filter for the same range, minus credits (reconciliation).
  - Outbox with the `none` adapter → rows `sent`; a throwing fake adapter → backoff, then `dead` after 5 attempts with an alert e-mail.
  - With `modules.pos` off → `placeOrder` creates no outbox row.
- E2E: `tests/e2e/attendance.spec.ts` (`06-TESTING.md` §3.3 #5).

## Acceptance criteria

- **AC-M3.3-01 [R10]** Given the admin's review QR, when it is scanned, then the phone opens Golden Grape's Google review form.
- **AC-M3.3-02 [R10]** Given a Places key, when the daily refresh runs, then the home page shows the rating, count and up to 5 recent reviews with Google attribution. Given no data, then the section is not shown.
- **AC-M3.3-03 [R10]** The admin shows the review overview, and either replies (if GBP access was granted) or a direct link to the Business Profile.
- **AC-M3.3-04 [R11]** Given today's venue QR, when an employee scans it and taps once, then they are checked in, the second tap checks them out, and yesterday's photo of the QR no longer works after 03:00.
- **AC-M3.3-05 [R11]** Given a missing check-out, when a manager corrects it with a reason, then the hours appear in the monthly report and the correction is in the audit trail. The CSV export matches the report.
- **AC-M3.3-06 [R8]** Given any date range, then the dashboard totals equal the order list totals for that range, and grouping by channel shows webshop, mobile and pos separately.
- **AC-M3.3-07 [R3]** Given a CashMag daily CSV, when it is imported, then the matched sales reduce stock with channel `pos`, unmatched rows are listed, and importing the same file again is refused.
- **AC-M3.3-08 [R3]** Given no POS connected, then every channel sells normally and the outbox shows no pending backlog.
- **AC-M3.3-09 [R9]** Given `modules.attendance` or `modules.reviews` switched off, then their staff routes return 404, their admin views are hidden, and the review section disappears from the site.
