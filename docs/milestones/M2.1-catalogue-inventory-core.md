## Goal

The product catalogue with variants and packaging units, plus **the single stock writer** `inventory.postMovements`. It is correct under concurrency, converts packaging to base units, and leaves an auditable ledger. After M2.1 the admin can create a product in 4 languages with a box of 6 and a box of 12, adjust stock with a reason, run a stock count, and see every movement with its user and reason. Nothing can oversell.

## In scope / out of scope

- **In:** the tasks below.
- **Out:** the public shop UI (M2.2), orders (M2.3), mobile screens (M3.1), purchase receipts (M3.1), low-stock **e-mail** (M3.1; the flag and admin list are built here).

## Tasks

### T1 · Catalogue collections
Files: `modules/catalogue/collections.ts`, `modules/catalogue/service.ts`.

- `categories`, `brands`, `products`, `variants` and `packagingUnits`, exactly as `04-DATA-MODEL.md` §2, with conditional admin fields (`wine` group when `kind = wine`, `snack` group when `kind = snack`).
- Hook: when a product is created with no variant, create its default variant (label = product name). It is idempotent.
- Validation hooks: `packagingUnits.factor ≥ 2`; barcodes are digits only (EAN-8/13, UPC-A 12, or internal codes) and unique across **variants and packaging units together**. One barcode must resolve to exactly one thing, so check both collections in a `beforeValidate`.
- Check how Mongo stores localized fields (for example `name.fr`) and declare the text index on those paths in the collection's `indexes`. Record the verified path in the data model doc.
- `service.ts`: `findByBarcode(code)` returns `{ variant, unit?, factor }` (it checks packaging first, then variants); `findSellable(ids, channel)`; `listProducts({ locale, category?, q?, page })` (used by M2.2).

### T2 · Packaging conversion (pure)
Files: `modules/catalogue/packaging.ts` (+ test).

- `toBaseQty(unitQty, factor)`; `normalizeLines(lines)` merges lines by variant into base quantities. Throws on a non-integer or `factor < 1`.
- Vectors: `06-TESTING.md` §3.1 M2.1, plus a merge vector (`[{v1, box6 ×1}, {v1, base ×2}]` → `{v1: 8}`).

### T3 · `postMovements` (the only stock writer)
Files: `modules/inventory/collections.ts`, `modules/inventory/service.ts`.

- Collections `stockLevels`, `stockMovements` and `stockCounts` with the access in `04-DATA-MODEL.md` §2 (no API writes to levels or movements).
- `postMovements(tx, lines: { variant, unit?, unitQty, type, reason?, channel, ref, user? }[])` first **drops lines whose variant has `trackStock: false`** (snacks, gift cards). It then implements `02-ARCHITECTURE.md` §5.1 steps 1–5 using `tx.session` for the conditional `$inc` and `payload.create(..., { req: tx.req })` for the movement rows. It recomputes `lowStock = onHand ≤ (threshold ?? settings.alerts.defaultLowStock)` in the same update with an aggregation-pipeline update, or a second update in the same session if the driver version lacks it.
- `onHand(variantIds)` and `availability(variantIds)` → `{ inStock, maxQty }` (the public projection).
- `scripts/rebuild-stock.ts [--check]` recomputes the totals from the ledger. `--check` exits 1 if any cache value differs.

### T4 · Adjustments and counts
Files: `modules/inventory/actions.ts`, admin components `modules/inventory/admin/{adjust-button,post-count-button}.tsx`.

- `adjustStock` (roles: admin, manager, stock): `variant`, signed `qty ≠ 0`, `reason` (≥ 3 chars, chosen from a short list plus "other": `breakage`, `tasting`, `gift`, `theft`, `correction`, `other`). Calls `postMovements` with type `adjustment`. An adjustment may not take `onHand` below 0 (same guard as a sale).
- An "Adjust stock" button sits on the variant edit view in the admin (`admin.components`). Payload has no form for this, so a custom component is allowed (law 1).
- Stock counts: staff create a count (lines added in the admin, or by scan in M3.1). `postCount(countId)` snapshots `expected` from `stockLevels` **inside the transaction**, writes a `count` movement per line with `counted − expected` (skipping zeros), sets `posted`, and is idempotent (posting a posted count is a no-op).
- Low-stock admin view: a list filtered by `stockLevels.lowStock = true` (Payload list view with a default filter; no custom screen).

### T5 · Movement history visibility
- On the variant edit view, show the movement list as a Payload `join` field (if the installed version supports joins on Mongo) or a small custom list component: date, type, qty (base units), unit label, reason, user and ref link, sorted newest first and paginated (index `{ variant, createdAt: -1 }`).

### T6 · Catalogue import (DEP-04)
Files: `scripts/import-catalogue.ts`, `docs/templates/catalogue-template.csv`.

- Template columns: `sku, barcode, name_fr, name_en, name_de, name_pt, kind, category_slug, brand, region_fr, vintage, colour, vat_class, price_eur, cost_eur, box6_barcode, box6_price_eur, box12_barcode, box12_price_eur, supplier, supplier_ref, opening_stock, low_stock`.
- The import is idempotent by `sku` (upsert). Opening stock is posted as **one `adjustment` movement** with reason `opening stock`, only if the variant has no movements yet. Every row is validated **before any write**. If any row is invalid, it prints a row-numbered error report and writes nothing. Supplier columns are stored for M3.1 (`supplierProducts` is created then; until M3.1 the import stores them in a staging JSON next to the import log).
- Until DEP-04 arrives, `scripts/seed.ts` loads the prototype's 18 shop products and 6 snack items (prices from the arrays, texts from the dictionaries). The seed calls the same upsert functions as the import, so the import path is exercised. After that, the catalogue keys are deleted from the dictionaries (M1.2 T2).

### T7 · Tests
- Unit: `packaging.test.ts` (T2).
- Integration (`modules/inventory/inventory.int.test.ts`):
  - 20 parallel `sale` posts of 1 against `onHand = 5` → exactly 5 succeed, 15 throw `OUT_OF_STOCK`, `onHand = 0`, 5 sale movements.
  - A sale of 1 × box6 → −6; a receipt of 1 × box12 → +12 (receipt type is called directly here; the receive UI is M3.1).
  - An adjustment records `user` and `reason`; an adjustment below 0 throws.
  - A count with expected 10 and counted 7 → one movement −3; posting again → no new movement.
  - `rebuild-stock --check` → 0 differences after all of the above.
  - A barcode used on a variant cannot be reused on a packaging unit.
  - A sale of a `trackStock: false` variant writes no movement and never throws `OUT_OF_STOCK`.

## Acceptance criteria

- **AC-M2.1-01 [V-SHOP] [V-I18N]** Given an admin creates a wine in 4 languages with price, VAT class and barcode, then all 4 translations, the default variant and a `stockLevels` row at 0 exist.
- **AC-M2.1-02 [R12]** Given a variant with box6 and box12 units, when a sale of 1 × box6 and a receipt of 1 × box12 are posted, then `onHand` changes by −6 and +12, and each movement shows the unit and base quantity.
- **AC-M2.1-03 [R1]** Given any stock change, then the variant's movement history shows date, type, quantity, user and reason, and no API role can edit or delete a movement.
- **AC-M2.1-04 [R2] [R1]** Given 5 in stock and 20 concurrent single-unit sales, then exactly 5 succeed and stock is 0, never negative.
- **AC-M2.1-05 [R1]** Given `lowStockThreshold = 3` and stock falls to 3, then the variant appears in the low-stock list.
- **AC-M2.1-06 [R1]** Given a posted count, then `rebuild-stock --check` reports no difference and the count can no longer be edited.
- **AC-M2.1-07 [V-SHOP]** Given the catalogue CSV with one invalid row, then the import writes nothing and reports the row number and reason.
